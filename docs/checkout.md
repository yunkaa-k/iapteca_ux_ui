# Оформление и демонстрационная оплата

Источники: Screens `2675:14017` (форма карты), `2877:25272` (оплаченный результат), `2487:12281` (ошибка и повтор). Общие Header/Footer, поля, карта и стили checkout переиспользуются. По указанию пользователя отдельная ссылка «Аналоги препаратів» из Footer удалена.

## Проверка

### Наличие общей аптеки — 25.11.2026

- `/checkout` — обычный выбор аптеки. Сочетание аптечки `travel` и Нурофена больше не блокирует самовывоз ни в интерфейсе, ни в API. Названия товаров не определяют доступность получения.
- `/checkout?pickup=unavailable` — локальная проверка состояния «Немає аптеки з усіма товарами» из Figma на той же корзине. Для сохранённой заявки: `/checkout?request=<id>&pickup=unavailable`. Параметр действует только при `NODE_ENV=development`; production его игнорирует. Дополнительных переключателей в продуктовом интерфейсе нет.
- В недоступном состоянии подтверждение заблокировано. «Обрати доставку» открывает адрес и переводит фокус в поле города, сохраняя контакты и способ оплаты. Возврат к самовывозу снова показывает недоступность. Обычную страницу можно открыть без параметра.
- Параметр проверки не входит в черновик, payload заказа или MongoDB. Проверка выполняется на уровне отображения, она не имитирует настоящий учёт запасов по филиалам. Сейчас база хранит общие остатки препаратов и компонентов; реальные остатки отдельных аптек не подключены. Существующие серверные проверки остатков и транзакции сохранены.

1. Добавить доступный товар или аптечку в корзину; для рецептурных позиций сначала пройти существующую проверку.
2. На `/checkout` заполнить контакты, выбрать получение и «Онлайн».
3. Только тестовые данные: `4242 4242 4242 4242` — успех; `4000 0000 0000 0002` — ошибка. Срок действия — будущий месяц/год, CVV — три тестовые цифры, например `123`.
4. Успех показывает «Замовлення оформлено та оплачено!». При ошибке заказ сохраняется. «Повторити оплату» только открывает пустую форму карты; запрос отправляется после проверки полей и нажатия «Підтвердити оплату». Повторный ввод `4000 0000 0000 0002` снова даёт ошибку, `4242 4242 4242 4242` — успех. Отмена закрывает форму без запроса. Повтор не обращается к банку и не создаёт новый заказ.

Форма явно обозначена как демонстрационная. Реальные карты не принимаются, платёжный провайдер не подключён, деньги не списываются. PAN, CVV и срок действия находятся только в локальном React-состоянии; не отправляются API, не попадают в Zustand, browser storage, MongoDB или логи. При смене способа оплаты и успешном сохранении заказа поля очищаются. Валидация не допускает произвольные номера карт.

## Совместимость и сервер

Сохранены `on-receipt` и старый `online-after-confirmation` для ранее созданных заказов и клиентов. Новая форма использует `online`. Старый черновик с оплатой после подтверждения открывается в новом онлайн-режиме с пустыми полями карты и требует повторного ввода тестовых данных.

`parseCheckout` принимает только whitelist полей контактов/получения и `demoPaymentOutcome: success | failure`. Сервер сам формирует `paymentMode: demo` и `demoPaymentStatus: paid | failed`; переданный клиентом статус не используется. Цена, доставка и остатки по-прежнему проверяются существующим транзакционным POST заказа. Итог оплаты хранится в MongoDB вместе с заказом. Ошибка демонстрационной оплаты не отменяет созданный заказ и не возвращает зарезервированные остатки.

POST `/api/orders/[id]/demo-payment` меняет только демонстрационный статус оплаты существующего активного заказа. Не создаёт новый заказ, не меняет сумму и не касается склада. Повтор после потерянного ответа идемпотентен; оплаченный заказ не переводится в ошибку. Отменённые/завершённые заказы исключены условием обновления. Обрабатываются ошибки сервера и повторные клики.

Для вошедшего пользователя проверяется владелец заказа. Гость получает при создании онлайн-заказа случайный 256-битный ключ; в БД хранится только SHA-256 хеш с `select: false`. Исходный ключ возвращается только при создании и хранится в receipt текущего sessionStorage. Передаётся через Authorization, не через URL. По обычному ID публичный доступ не добавлен; после потери браузерной сессии гость не может повторно открыть оплату. Администратор продолжает видеть гостевые заказы через существующий административный API.

В «Мої замовлення» повтор доступен в деталях существующего заказа. Подтверждение гостевого результата использует существующий receipt; сервер не предоставляет публичный поиск по ID. Prototype-переход повторной оплаты отдельно через MCP не проверен. По уточнению пользователя повтор использует существующую форму карты непосредственно на экране результата/в деталях заказа; открытие формы никогда не подтверждает оплату автоматически. API требует явный `outcome` новой демонстрационной попытки и отклоняет пустой запрос; реквизиты по-прежнему не передаются.

## Детали и отмена заказа — 23.11.2026

Изучены текущие Screens: `2487:12195` (обработка), `2487:12324` (оплата подтверждена), `2232:8496` (готово к выдаче), `2473:11927` (передано курьеру), `2232:9011` (получено), `2487:12410` (отменено), `2487:12367` (возврат в обработке), `2461:12048` / `2492:13839` (подтверждение обычной / оплаченной отмены). Снимки и design context использованы для переноса экранов; полнота Prototype-переходов отдельно не подтверждена.

`/profile?tab=orders&order=<id>` открывает `OrderDetails.tsx`. Сервер по-прежнему выбирает только заказы вошедшего пользователя; неизвестный/чужой ID показывает «Замовлення недоступне». В деталях — сохранённые товары, количества, сумма с доставкой, статус, контакты, аптека либо адрес курьера. Список товаров `OrderProducts.tsx` переиспользуется в заявках на рецепты. Старые заказы без checkout остаются читаемыми, отсутствующие данные не выдумываются.

Складской статус и оплата отображаются отдельно: оплаченный заказ в обработке сохраняет жёлтый badge «В обробці» и зелёное уведомление об оплате. Добавлены `READY_FOR_PICKUP` / `SHIPPED` в типы, Mongoose и существующий административный список статусов. Они не назначаются автоматически по таймеру: администратор выбирает их при подготовке/передаче. API проверяет соответствие самовывозу/курьерской доставке. `CONFIRMED` сохранён для совместимости и не приравнивается к готовности.

PATCH `/api/orders/[id]` разрешает владельцу только отмену своих `PENDING`, `CONFIRMED`, `READY_FOR_PICKUP`; чужой/гостевой заказ для покупателя недоступен. После передачи курьеру или получения пользовательская отмена запрещена. Существующие административные возможности сохранены. Диалог показывает разные тексты для оплаченного и неоплаченного заказа. «Залишити замовлення»/Escape не отправляют запрос, повторные клики заблокированы, ошибка остаётся в диалоге.

Статус и возврат всех остатков выполняются одной транзакцией MongoDB. Для аптечек используется состав, сохранённый в заказе, умноженный на количество наборов. Повторная отмена возвращает текущее состояние без повторного списания/возврата. Конфликты записи повторяются с новым чтением состояния. У отменённого оплаченного демозаказа атомарно сохраняется `checkout.demoRefundStatus: pending`: это демонстрация, банковского перевода нет. Административное восстановление отменённого заказа заново резервирует компоненты в той же транзакции и очищает демонстрационную отметку возврата.

Повтор оплаты разрешён только для активных `PENDING`, `CONFIRMED`, `READY_FOR_PICKUP`; после отмены, передачи курьеру и завершения кнопка скрыта, API также отклоняет запрос. Конкурирующие повтор оплаты и отмена не могут оставить оплаченный отменённый демозаказ без отметки возврата: запись заказа участвует в проверке конфликта транзакции.

Безопасная локальная интеграционная проверка: `node scripts/test-local-order-cancellation.mjs` при запущенном Next.js на `http://localhost:3000`. Скрипт допускает только loopback MongoDB, базу `iapteca`, PRIMARY `rs0`; создаёт уникальные временные данные и удаляет только их. Проверяет права владельца, смешанный заказ, три параллельные отмены, повторную отмену, снимок состава, отмену оплаченного демозаказа, гонку оплаты/отмены и точный возврат остатков. Секреты не печатаются. Скрипт прошёл на локальной MongoDB. В браузере отдельно проверены оплаченный заказ, отказ от отмены, подтверждение и сохранённый результат возврата; временные записи удалены, реальный каталог не менялся.

## Развёртывание

После изменения Mongoose-схемы перезапустить dev-сервер: горячая перезагрузка может оставить ранее скомпилированную модель в `mongoose.models`. Миграция или перезаполнение данных не требуется; новые поля необязательны. Демонстрационные статусы не являются доказательством реальной оплаты и не должны использоваться для реальных продаж.

## Локальные демонстрационные заказы — 23.11.2026

По запросу пользователя в локальную базу добавлены 9 отдельных заказов для существующего аккаунта Антон Тарас. Настоящие заказы не менялись. Проверять в `/profile?tab=orders`: обработка, подтверждено, готово к выдаче, передано курьеру, получено, отменено без оплаты, оплачено онлайн, ошибка оплаты, отменено с возвратом в обработке. Оплата/возврат — демонстрационные, независимо от складского статуса.

`scripts/seed-local-order-states.mjs <existing-user-id>` показывает сценарии; `--apply` создаёт только недостающие записи. Скрипт допускает только loopback MongoDB `iapteca`, rs0 PRIMARY, требует существующий аккаунт и проверяет коллизии детерминированных ID. Не создаёт пользователей, не выводит секреты, не перезаписывает уже проверенные/отменённые сценарии.

Используется отдельный скрытый `inventoryOnly` тестовый товар с явно демонстрационным названием; активные/полученные сценарии списывают только его остаток внутри транзакции создания. Отмена такого заказа возвращает только этот тестовый товар. Реальные остатки, Bundle и витрина не затрагиваются. `AccountOrders.tsx` отмечает такие заказы подписью «Демонстраційне замовлення»; названия строк начинаются с `[ДЕМО]`. Контакты синтетические. Повтор запуска подтвердил 0 новых заказов; чтением проверены 9 сценариев и изолированный остаток 993 из исходных 1000. После ручных отмен остаток закономерно изменится; повтор seed не сбрасывает результаты тестирования.
