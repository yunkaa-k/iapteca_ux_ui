# iApteca — карта соответствия Figma и исходного кода

> Уточнение после очистки 20.11.2026: таблицы ниже сохраняют исходный аудит 08.11 и не являются текущим перечнем готовности. Промокоды исключены из проекта; прежние указания сохранять их отменены. Выдвижная корзина удалена как неиспользуемая: актуальная реализация — `src/app/cart/page.tsx`, `src/components/CartPage.tsx` и существующий `cartStore`. Актуальная архитектура описана в [architecture.md](architecture.md).

Актуализация: 2026-11-08.

## Область карты

- Продуктовые экраны, состояния и сценарии взяты только со страницы Figma **Screens**; UI-Kit используется как источник общих компонентов и дизайн-системы.
- На Screens подтверждено 71 desktop-кадр шириной 1440 px. Мобильные макеты в текущий охват не входят до их отдельной подготовки в Figma.
- Статусы: **Готово**, **Частично реализовано**, **Не реализовано**, **Требуется проверка**. Ни один экран не отмечен «Готово»: текущая реализация визуально и функционально не совпадает с целевыми макетами целиком.
- Проверка рецептов и выбор аптеки — демонстрационные, без реальных интеграций, но с сохранением предусмотренных состояний.
- Основной язык UI — украинский. MongoDB и существующие API переиспользуются; модели можно расширять при необходимости.
- Маршруты в таблице — целевая структура, а не уже существующие страницы. Состояния одного сценария размещаются внутри общего маршрута, где это подходит.

## Текущие и предлагаемые маршруты

| Назначение | Сейчас | Предлагается |
|---|---|---|
| Главная | / показывает упрощённый каталог | / — домашняя страница из Figma |
| Каталог/поиск/фильтры | Логика в src/app/page.tsx | /catalog |
| Товар | /product/[id] | Сохранить /product/[id] |
| Корзина | Только выдвижной CartDrawer | /cart |
| Сравнение | Нет | /compare?products=id1,id2 |
| Готовые аптечки | Нет | /kits и /kits/[id] |
| Оформление | Базовая форма на /checkout | Сохранить /checkout и расширить |
| Результат заказа | toast → /profile | /order/result со state success/error и вариантами результата |
| Авторизация/профиль/admin | Существуют | Сохранить текущие маршруты и функции |

### 1. Multi-Rx: две отдельные ветки проверки

Кадры имеют один заголовок и одинаковые товары/вложения, но различаются copy и выходом Prototype:

| Кадр | Текст состояния | Содержание | Prototype |
|---|---|---|---|
| 1611:8942 | «Рецепти перевіряє фармацевт»; «Після підтвердження обох позицій можна продовжити оформлення.» | Амоксицилін 500 мг №10 и Азитроміцин-Дарниця 500 мг №3; у обоих показано «Рецепт прикріплено» и имя файла | AFTER_TIMEOUT → RX Multi / Рецепти підтверджено (1611:9544) |

Оба результата воспроизводить одинаковой задержкой Prototype. Для ветки отказа пройти замену файла и повторную проверку. ### 2. Авторизация при checkout

В Screens кадры checkout 164:123 и 1677:18635 содержат поля контактных данных (имя/фамилия, телефон, email), способ получения, summary заказа и validation state. Прототип ведёт из корзины непосредственно к checkout, а из заполненного checkout — к Order Success. В Screens нет кадра входа/регистрации как обязательного шага и нет перехода checkout → login. Визуально поток рассчитан на ввод контактных данных без обязательного входа; отдельной надписи «гость» в Figma нет, поэтому корректнее считать гостевой сценарий предусмотренным, но не сформулированным отдельным требованием.

В коде src/app/checkout/page.tsx функция handleOrder (около строк 67–86) перенаправляет неавторизованного пользователя на /login до POST /api/orders. В src/app/api/orders/route.ts функции GET и POST требуют getAuthUser() и отвечают 401 без пользователя. src/lib/auth.ts получает пользователя из cookie auth_id. src/app/profile/page.tsx также защищён redirect на /login.

Варианты согласования:

1. **Сохранить Figma guest checkout и разрешить гостевой POST заказа.** Для гостя API сохраняет контактные данные и заказ без user ID; для вошедшего пользователя сохраняется текущая привязка user. Старые записи и авторизованные заказы продолжают работать. Потребуется продумать защищённый доступ гостя к результату/повторному просмотру заказа.
2. **Сохранить API auth-only и добавить вход/регистрацию в UX до отправки.** Нужно явно добавить в дизайн шаг/гейт авторизации; это меняет текущий Prototype и добавляет трение в сценарий.
3. **Оставить checkout демонстрационным и не создавать запись для гостя.** Минимум изменений API, но обычный успешный сценарий не сохраняется в существующей MongoDB, поэтому вариант не соответствует цели переиспользовать API.

Рекомендация для точного соответствия Screens — вариант 1, сохранив текущую авторизацию и привязку заказов для вошедших пользователей. Это требует согласования, так как меняет контракт POST /api/orders.

### 3. Kit: минимальная модель и совместимость заказов

Figma для «Аптечка “Для подорожі”» показывает цену 249 грн и «Демонстраційний набір першої допомоги · 3 позиції»; состав — пластыри, стерильный бинт и антисептические салфетки. Это похоже на самостоятельный товарный SKU-набор. При этом Cart / Готова аптечка (1690:8858 и 1742:8741) показывает «Товари (2 позиції)», две отдельные позиции Нурофен 200 мг №24 и Ібупрофен-Дарниця №20, сумму 224 грн; кадры отличаются названием сценария, но отображаемый состав/сумма одинаковы. Order Success для одного и двух наборов также показывает те же две позиции и 224 грн. Это противоречит карточке набора за 249 грн и не подтверждает, должно ли содержимое раскрываться в корзине или оставаться одной строкой.

Текущее Medication в src/lib/types.ts / src/lib/models.ts хранит name, description, price, stock, category, manufacturer и image. OrderItem — medication id, quantity, price. POST /api/orders в src/app/api/orders/route.ts уменьшает stock через MedicationModel.findOneAndUpdate и сохраняет эти OrderItem; отдельной Kit модели или API нет.

| Вариант | Представление | Совместимость и цена |
|---|---|---|
| Kit как отдельный каталоговый SKU в Medication | Необязательный kind=KIT и kitContents в существующем товаре; строка заказа продолжает ссылаться через medication, а stock означает число готовых наборов | Минимальный путь: текущий Product/Cart/Order API и старые заказы остаются совместимыми. Подходит, если набор продаётся как готовая упаковка с собственным запасом |
| Отдельная Kit модель | Kit содержит заголовок, цену, изображение, позиции состава и, при необходимости, собственный stock; OrderItem получает явный тип и kit id/snapshot | Чище для управления набором, но требует новой модели/API и ветки обработки заказа. Старые элементы без типа нужно трактовать как обычный Medication |
| Разложить Kit на обычные Medication позиции | Набор преобразуется в дочерние строки существующих лекарств; опциональная group/bundle метка сохраняет группировку | Использует текущую резервацию stock, но не описывает аптечку из пластырей/бинта/салфеток как набор, а не все элементы являются Medication |

**Минимальная рекомендация:** если преподаватель/команда подтверждает, что это готовая продаваемая упаковка, использовать Kit как товар/SKU в существующем каталоге Medication с необязательным discriminator и структурой kitContents; OrderItem и обычный stock API тогда сохраняются. Если состав должен быть изменяемым или независимо управляемым — отдельная Kit модель и типизированная позиция заказа лучше, но это больший этап. До выбора проверить расхождение Figma для каталога, cart и order result.

### 4. Состояние Rx между маршрутами

Для переходов cart → checkout → result UI должен сохранить для каждой Rx-позиции: стабильный id строки/Medication, факт необходимости рецепта, имя демонстрационного файла или fixture, статус (required, attached, reviewing, approved, needs-new-photo), номер попытки/повторной загрузки и выбранный demo outcome. Для Multi-Rx нужно сохранить связь каждого файла с конкретным препаратом/слотом; одного общего флага «рецепты загружены» недостаточно.

Данные одного рецепта: один Medication/cart line, один file label/fixture, состояние проверки и результат. Данные двух рецептов: два отдельных элемента с medication id, slot/position, file label/fixture и собственным результатом; общий flow status можно вычислять из двух результатов. Figma использует две отдельные карточки Амоксициліну и Азитроміцину и показывает отдельный статус вложения для каждой.

**Демонстрационная рекомендация:** расширять существующее serializable состояние корзины либо рядом добавить небольшой prescription demo store с session persistence. Существующий Zustand cartStore уже persist-ит сериализуемую корзину в localStorage, поэтому состояние может пережить навигацию и refresh. Не помещать объект File и бинарное содержимое в localStorage/MongoDB; хранить только fixture/file name и demo status. Перед clearCart после успешного POST сформировать receipt snapshot в sessionStorage или result store, чтобы экран результата не зависел от уже очищенной корзины. Сохранять Rx в Order/MongoDB имеет смысл только если его нужно видеть в истории заказов после завершения сессии.

### 5. Нулевое количество в корзине и результаты заказа

В src/lib/store/cartStore.ts функция updateQuantity при q <= 0 вызывает removeItem; removeItem фильтрует строку из items. Нулевое количество не сохраняется как cart item. Это соответствует семи Figma-вариантам 53–59: Nurofen/ибупрофен представлены комбинациями 0, 1 и 2; при переходе к нулю товар удаляется, а в остальных строках пересчитываются количества/итог. Уже существуют ограничения: addItem не добавляет товар с stock 0, updateQuantity не допускает количество выше stock.

Кадр 1547:3970 «3 of 5 products» показывает «Показано 3 з 5 товарів» и кнопку «Показати ще 2». Кадр 1568:4020 раскрывает весь список и показывает «Усі 5 товарів» с действием «Згорнути». Prototype по клику переключает 3/5 → all 5 и обратно. Это свернутое/развернутое отображение списка, а не частичная комплектация, отгрузка или частичный успех заказа.

**Демонстрационная рекомендация:** строить обе версии из одного набора из пяти заказанных строк: по умолчанию показывать первые три и control «Показати ще 2», при раскрытии — все пять; «Згорнути» возвращает компактный список. Не добавлять частичный stock/fulfillment state для этих кадров. Для реального заказа брать order items из созданного заказа, а не из cart после очистки.
