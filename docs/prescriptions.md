# Рецепты: desktop и демонстрационная проверка

Источник: актуальная страница Screens в Figma, проверена 20.11.2026.

- `2329:9144`: информационная страница «Як придбати ліки за рецептом» → `/prescription`. Ссылки «Рецепт» в Header и «Електронний рецепт» в Footer ведут сюда.
- `1177:6922`: пустая корзина → `/cart`; иконка тележки, отсутствие ссылки назад в заголовке, кнопка «Перейти до каталогу», размеры из Figma.
- `1604:4575`: рецептурная корзина → активная кнопка «Перейти до перевірки рецепта» → `/cart/prescription`.
- `1604:4898`, `1604:5138`, `1604:5384`, `1604:5620`, `1604:5859`, `1611:8112`: добавление, замена, удаление файлов, ожидание, подтверждение, запрос нового фото и отдельные слоты для нескольких препаратов.

## Демонстрация

1. Добавьте в корзину рецептурный препарат (например, Амоксицилін).
2. Перейдите к проверке и выберите непустой JPG, PNG, WEBP или PDF размером до 10 МБ. Это проверка формата и размера, а не чтение рецепта.
3. Нажмите «Надіслати на перевірку». Через 8 секунд обычное имя файла даёт статус «Рецепт підтверджено».
4. Для воспроизведения ветки нового фото назовите демонстрационный файл `blur.jpg` (либо добавьте `нечитабельн` в имя). После проверки появится «Потрібне нове фото». Замените его файлом без этого маркера и отправьте повторно.
5. При двух рецептурных товарах прикрепите файл к каждому. Можно выбрать уже добавленный файл для другой позиции. Подтверждение одной позиции сохраняется при замене файла другой.
6. До подтверждения всех рецептов UI не позволяет перейти к оформлению; прямой переход на `/checkout` показывает ссылку на проверку. После подтверждения доступна существующая страница оформления.

Проверка — локальная имитация, не заключение фармацевта. Изображения и медицинские документы не отправляются в API и не записываются в MongoDB. В `sessionStorage` сохраняются только имя файла, идентификатор товара, количество, статус и время завершения имитации. Обновление страницы и переходы сохраняют состояние в текущей вкладке. Изменение количества/удаление товара сбрасывает его подтверждение. Успешное создание заказа очищает демо-состояние.

## Границы

Список и детали заявок теперь реализованы в «Мої замовлення». Перед первым сохранением заявки гость видит вход из кадра `2484:12125`; после входа/регистрации возвращается к прикреплённому файлу, затем отправляет его на проверку. Вкладки входа и регистрации сохраняют этот контекст; внешние return URL не принимаются.

`prescriptionRequestStore` хранит в sessionStorage снимок товаров и имён файлов, дату, статусы и ID владельца. Заявки отделены от текущей корзины и показываются только соответствующему аккаунту. Переходы и обновление страницы в этой вкладке сохраняют состояние. Проверка завершается также после перехода в профиль. Закрытие вкладки очищает демонстрационную историю; синхронизации между устройствами и серверной истории рецептов нет.

- `/profile?tab=orders` — заявки и существующие реальные заказы MongoDB.
- `/profile?tab=orders&request=<id>` — детали ожидающей/подтверждённой заявки или запроса нового фото (`2344:9677`, `2344:9726`, `2344:9775`). Это локальная заявка текущего аккаунта; публичного API поиска заказов по ID нет.
- `/cart/prescription?request=<id>&from=details` — замена файла в заявке с возвратом к деталям. Другие подтверждённые рецепты сохраняются.
- `/checkout?request=<id>` — существующее оформление по снимку подтверждённой заявки. Посторонние товары текущей корзины не включаются в этот заказ и не удаляются после его успеха.

Отмена заявки использует диалог `2461:12074`; повторная отмена ничего не меняет. Заявка ещё не списывала товар, поэтому отмена не меняет склад и не вызывает API отмены реального заказа. После успешного создания заказа заявка помечается оформленной и исчезает из незавершённых.

Полная форма checkout, оплата и получение остаются отдельным этапом. Серверный API заказов этим изменением не превращается в медицинскую систему проверки рецептов.

## Проверки

Автоматические сценарии покрывают независимость слотов, обязательность всех файлов, дедлайн проверки, восстановление сериализованного состояния, новый файл после отказа, инвалидирование подтверждения при изменении количества и валидацию формата. Данные реальных заказов эти проверки не создают.
