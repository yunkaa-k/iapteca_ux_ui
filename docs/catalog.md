# Desktop-каталог iApteca

Основа: актуальные Screens `164:42`, `629:568`, `1177:2473`, `1229:1065`, `1229:1919`. Реализация: `/catalog`, `SearchAndFilters`, `Catalog.module.css`, общий `ProductCard`, `Pagination` и существующий MongoDB `MedicationModel`.

Реализованы поиск по названию и явно заданному действующему веществу, категории, шесть лекарственных форм, наличие, диапазон цены, сортировка, пагинация, чипы удаления условий и сброс. Дополнительные фильтры раскрываются через доступный details/summary. Цена меняется числовыми полями и двумя ползунками Radix (нижняя и верхняя границы); изменения применяются при Enter или выходе из формы, при отпускании ползунка и клавиатурном управлении.

Состояние хранится в URL. Смена фильтра сбрасывает страницу выдачи. Назад/вперёд восстанавливают выбранные условия и запрос. Сброс фильтров сохраняет поисковый запрос; переход ко всем товарам очищает и запрос. Отдельно отображаются пустая база, пустой поиск и пустая выдача фильтров.

## Данные

Локальный демонстрационный каталог: `pnpm seed:local`. Скрипт принимает только MongoDB на localhost/127.0.0.1:27017, базу iapteca, Replica Set rs0 и authSource=iapteca. Добавление выполняется транзакцией; существующие товары с совпадающим именем сохраняются без изменений. ID новых товаров устойчивы, повторный запуск не пополняет остатки и не создаёт дубликаты. Пользователи, заказы и секреты не затрагиваются.

В seed включены 11 карточек Screens 164:42. Названия, цены, дозировки, упаковки и изображения взяты из этих карточек; сведения об ибупрофене и явно указанной безрецептурности — из соответствующих Product Details. Остатки условные, для учебной демонстрации: 10 товаров доступны, Ибупрофен 400 мг №20 отсутствует. Рецептурность остальных товаров не предполагается автоматически. Производитель, страна, возрастные ограничения и официальные инструкции требуют отдельного проверенного источника. Все записи помещены в общую категорию «Препарати»; классификация по назначению не выдумывается. Аптечки Bundle этим seed не создаются.

Страница `/product/[id]` использует `ProductDetails` и существующие MongoDB Medication. Добавлены характеристики, раскрывающиеся секции, выбор количества, корзина, избранное и сравнение до трёх вариантов с текущим товаром. Варианты подбираются по явно заданному действующему веществу, без вывода состава из названия. Для отсутствующего товара показываются только доступные варианты. Неизвестная рецептурность не трактуется как безрецептурный отпуск. Цена за единицу рассчитывается только при заполненном `packSize`.

Официальная инструкция пока не хранится в модели: секция показывает описание и явное сообщение об отсутствии официальной инструкции. Доставка отображает общие сведения из макета; расчёт и выбор аптеки остаются следующим этапом. Наполнение проверенными товарными данными и визуальная проверка заполненных экранов ещё необходимы.

Добавлены необязательные поля Medication: `dosageForm`, `dosage`, `packSize`, `requiresPrescription`, `activeIngredient`, `country`, `atcCode`, `brand`, `ageGroup`, `packageType`, `onSale`.

Лекарственные формы: tablets, capsules, suspensions, powders, ointments, dragees. Остальные характеристики берутся из проверенных данных товара, не выводятся автоматически из его названия. Отсутствующий `requiresPrescription` означает неизвестную рецептурность: такой товар не попадает в фильтр «Без рецепта» как якобы подтверждённый безрецептурный препарат.

Счётчики форм и варианты списков получаются из неудалённых товаров базы, а не из фиксированных чисел макета. Если в базе пока нет дозировок и размеров упаковки, отображаются проверенные варианты Figma; выбор такого условия даёт пустую выдачу. Их значения не присваиваются существующим товарам. Цена по умолчанию не ограничивает выдачу; шкала ползунков начинается с 0–10 000 грн и расширяется, если максимальная цена базы выше. Явно выбранные границы сохраняются в URL.

Старые записи и заказы сохраняют совместимость. Новые поля можно передать существующему административному Medication API; отдельные элементы ввода этих характеристик в административной форме ещё предстоит добавить. Наполнение согласованными товарами и фотографиями выполняется отдельным этапом. Seed не запускается.

## Проверка

### Повторное переключение фильтров — 23.11.2026

В браузере воспроизведён случай: один фильтр рецептурности → оба → один. Сервер считал правильные 10/11/1, но клиент мог оставлять прежнюю выдачу. `SearchAndFilters.tsx` теперь получает `queryString` вместе с серверными карточками из `src/app/catalog/page.tsx`: checkbox, chips и результаты относятся к одному завершённому запросу.

Для обхода воспроизведённого повторного использования старой выдачи в клиентской навигации Next 16.2.4 каждому изменению фильтров/поиска/сортировки и сбросу добавляется новый служебный `_revision`. Предыдущее значение заменяется; оно не участвует в MongoDB-фильтре, не отображается среди chips и не требует изменения зависимостей. URL остаётся доступным для копирования. Это локальный обход, а не доказательство конкретной причины внутри Next: в проекте Next также есть [исправление ключей кеша search params](https://github.com/vercel/next.js/pull/94144), но его описание касается другой воспроизводящей конфигурации. При отдельном согласованном обновлении Next обход можно пересмотреть после браузерной проверки.

Проверено в браузере без перезагрузки: OTC → оба → Rx = 10 → 11 → 1; Rx → оба → OTC = 1 → 11 → 10; дозировки 200 мг → 200 + 500 мг → 500 мг = 2 → 4 → 2; удаление chip и общий сброс возвращают 11 товаров. Регрессионные тесты `src/test/catalog-controls.test.tsx` проверяют согласованность серверного snapshot, повторные сочетания и сохранение остальных условий.

`pnpm test:run`, `pnpm exec tsc --noEmit`, `pnpm lint`.

При запущенном Next.js и локальной MongoDB: `node scripts/test-local-catalog.mjs`. Скрипт допускает только локальную `iapteca`, создаёт помеченные случайным идентификатором программные тестовые записи (не реальные препараты), проверяет выдачу через HTTP и удаляет только свои записи. URI и секреты не выводятся.

## Категории — проверка 23.11.2026

Локальное чтение MongoDB подтвердило: все 11 видимых препаратов имеют `category: "Препарати"`. Поэтому переход с главной в `Шлунково-кишковий тракт` даёт пустую выдачу: `catalogQuery()` корректно ищет точное значение поля `Medication.category`. `CategoryModel` хранит список названий, а не автоматически классифицирует товары. Счётчики лекарственных форм сейчас относятся ко всему каталогу, поэтому ненулевой счётчик формы не гарантирует совпадений с выбранной категорией.

Минимальный следующий этап без изменения архитектуры: согласовать категории шести карточек главной; добавить их в `categories`; подготовить проверенное соответствие конкретных товаров категориям; обновить только `category` у этих товаров по существующему `_id`. Цены, остатки, изображения, другие характеристики и заказы не менять. Выполнять повторяемое обновление с предварительным списком изменений и локальной транзакцией; согласованные значения также внести в seed для новой базы. Повтор существующего insert-only seed сам по себе категории уже созданных товаров не исправит. Проверить переход с главной, выбор в каталоге, совместную работу с поиском/наличием/ценой и возврат назад. На этом этапе категории и товарные записи в БД не изменялись; назначения препаратов и неизвестные медицинские характеристики не выводились из названий.

Сортировка по реальной популярности и мобильная адаптация пока не входят в реализацию.
