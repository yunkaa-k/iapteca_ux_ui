# Передача проекта iApteca в новый чат

Актуализация: 23.11.2026. Этот документ описывает проверенный код ветки `dev`, а не прежние планы. Он не подтверждает покадровое pixel-perfect соответствие всей Figma. Исторические таблицы в других документах могут говорить «не реализовано» о функциях, которые уже появились: сверять с кодом и последующими разделами документов.

## 1. Назначение и обязательные ограничения

iApteca — учебная интернет-аптека команды SUPERNOVA для практической №3 Frontend System Design. Пользователь ищет препараты, выбирает категорию и фильтры, сравнивает аналоги внутри карточки, сохраняет избранное, покупает лекарства/готовые аптечки, проходит демонстрационную проверку рецепта и оформляет заказ. Интерфейс украинский.

- Продолжать существующий Next.js-проект. Упоминание React + Vite + JavaScript в старой переписке ошибочно: текущий проект Next.js + TypeScript.
- Figma не изменять. Продуктовые desktop-макеты брать только из `Screens`, компоненты/токены — из `UI-Kit`. Архив не является источником требований.
- В Figma обнаружена также страница `Mobile`; её перенос этим этапом не подтверждён и не выполнен. Мобильную работу согласовывать отдельно; в практической №3 адаптивность обязательна.
- Сохранять существующие MongoDB, API, тесты, модель складского учёта и рабочие функции. Не переписывать приложение и не менять стек без причины.
- Не добавлять телефонный вход, английскую локализацию, промокоды, Kubernetes, микросервисы, API Gateway, k6 или прежнюю observability-инфраструктуру.
- Карта, рецепты, онлайн-оплата и возвраты — демонстрационные. Настоящие письма, SMS, банк, медицинские проверки и внешняя карта не подключены.
- Изменять код по этапам. Commit/push выполнять по отдельному указанию пользователя; `main` не трогать без отдельного разрешения.
- Не читать/печатать секреты из `.env.local`, keyFile и backup. Не удалять Docker volumes, не сбрасывать БД, не перезапускать первоначальную настройку существующего окружения.

## 5. Каталог и данные

Серверная страница каталога строит MongoDB-фильтр через `catalogQuery`, загружает товары, total, категории и фасеты. URL — источник условий. Поиск по имени/веществу, категории, лекарственной форме, наличию, цене 0–10000, дозировке, упаковке, рецептурности и дополнительным характеристикам. Внутри одного multi-select условия объединяются как OR, разные группы — как AND. Два флага Rx/OTC означают оба типа, а не пересечение.

Сортировка UI: «Спочатку дешевші» / «Спочатку дорожчі». Старый URL `sort=newest` совместим с сервером, но не является новым пунктом макета. Счётчики лекарственных форм глобальные, а не пересчитанные относительно всех текущих условий.

Подсказки `/api/search/suggestions`: товары, история/популярные запросы и категории, исправление опечатки; история браузерная. Карточки переиспользуются на разных страницах; длинные имена не растягивают ряд. Нет товара — красная точка и подпись, покупка блокируется. Избранное и добавление сопровождаются уведомлениями.

На момент проверки локальный видимый каталог: 11 препаратов, 10 с явно заданным OTC и 1 Rx (Амоксицилін). Неизвестный флаг не приравнивается к false. Категории заполнены без админки: простуда — Парацетамол; боль — 5 товаров (Цитрамон, оба Ибупрофена, оба Нурофена); ЖКТ — Бісакодил; сердечно-сосудистые — Валідол; витамины — Ревіт; дерматология — Метилурацил с мірамістином; антибактериальные — Амоксицилін. Это учебная навигационная классификация, не назначение лечения.

`catalog-categories.json` и `catalog-prescriptions.json` содержат явные соответствия и ссылки на проверенные источники. `categorize-local-catalog.mjs` / `update-local-prescriptions.mjs` допускают preview, `--apply`, известные ID, только локальную rs0; создают backup и не меняют другие поля. Не придумывать отсутствующие медицинские характеристики: часть карточек закономерно показывает «Не вказано».

Последний баг повторных фильтров исправлен: контролы и товары получают один серверный `queryString`; навигации присваивается уникальный `_revision`, обходящий воспроизведённую старую клиентскую выдачу Next 16.2.4. Параметр не влияет на бизнес-фильтр/chips. Не удалять обход без браузерной регрессии: OTC → оба → Rx = 10 → 11 → 1; обратно 1 → 11 → 10; дозировки 200 → 200+500 → 500 = 2 → 4 → 2. Обновление зависимостей не выполнялось.

## 6. Хранение состояния и авторизация

| Где | Что хранится |
|---|---|
| MongoDB | User, UserSession, Category, Medication, Bundle, Order |
| HttpOnly cookie `auth_id` | Случайный 256-битный токен сессии; в MongoDB только SHA-256 токена, TTL и владелец |
| authStore | Клиентское представление авторизованного пользователя; полномочия проверяет сервер |
| localStorage | cartStore (`iapteca-cart`), favoritesStore (`iapteca-favorites`), searchHistoryStore |
| sessionStorage | prescriptionStore, prescriptionRequestStore, checkoutStore (черновики и receipt) |
| Состояние компонента | Демокарта и её CVV, пароли, локальные действия/ошибки; карточные реквизиты не сохраняются |

Email нормализуется; пароль bcrypt, минимум 8 символов/максимум 72 UTF-8 байта; новые роли только CUSTOMER. Сессия 24 часа, HttpOnly/SameSite=Lax/Secure в production; logout удаляет серверную сессию. Вход телефоном не поддерживается. Профиль действительно меняет данные и пароль после проверки текущего. Ошибки полей отображаются отдельно, toast «Зміни збережено», красный выход с подтверждением.

Восстановление через `/reset-password`: email → код 482913 → новый/повторный пароль → demo-итог. Письмо не отправляется, настоящий пароль аккаунта НЕ меняется. Незащищённый прежний `/api/auth/reset-password` закрыт ответом 503. Не подключать письма и не превращать это в реальную смену без отдельного задания.

## 7. Корзина, аптечки и склад

cartStore хранит товарный снимок и количество. Количество <= 0 удаляет строку. Добавление ограничено снимком stock, но окончательные цена/наличие проверяются сервером. Favorites bulk-add обновляет данные с API и пропускает недоступное; отдельная кнопка «Переглянути кошик» удалена по макету.

Bundle — отдельный готовый товар с фиксированным составом. Нет собственного stock: доступность = min floor(stock компонента / расход на набор). Состав покупатель не редактирует. `compositionConfirmed` и корректность компонентов обязательны. Материалы `inventoryOnly` хранятся в Medication, скрыты от покупательского каталога и не продаются отдельно.

Пять наборов: travel 249, home 349, auto 449, hiking 329, sport 379 грн. Только travel-состав взят из Figma (пластири, бинт, антисептические салфетки по одной упаковке); остальные составлены по отдельному разрешению пользователя как учебные наборы принадлежностей. Они не являются экспертной медицинской комплектацией или подтверждением стандартов. Подробный состав — `docs/bundles.md` и seed, не придумывать лекарственные дозировки.

Строка набора в Order имеет `kind=bundle`, snapshot состава, цену/название/изображение/slug. Старые строки без kind — обычные Medication. При покупке лекарства, одного/нескольких наборов или смешанного заказа сервер списывает агрегированные компоненты и сохраняет Order в одной транзакции. При дефиците всё откатывается. Цена/состав из браузера не являются источником складского списания.

Отмена: статус + возврат склада атомарны. Возврат Bundle — по сохранённому составу заказа, а не обновлённому Bundle. Повторная CANCELLED не возвращает остатки второй раз; конфликты транзакций ограниченно повторяются. Клиент может отменить только свой PENDING/CONFIRMED/READY_FOR_PICKUP. SHIPPED/COMPLETED пользователь не отменяет. Административные изменения имеют отдельные права и проверки метода получения.

## 8. Рецепты и заявки

JPG/PNG/WEBP/PDF, непустой, до 10 МБ. Только demo: содержимое не распознаётся, файл не отправляется на сервер и не записывается в MongoDB. Сохраняются метаданные (имя/количество/статус/deadline). Через 8 секунд обычное имя → approved; `blur`/`нечитабельн` в имени → needs-new-photo. Можно заменить файл, повторить, использовать ранее добавленный для другого слота. Слоты независимы; изменение количества инвалидирует подтверждение.

Заявка `prescriptionRequestStore` — отдельный снимок товаров с ownerId, а не весь текущий cart. Для сохранения нужен вход; после него возвращаемся в контекст. Есть reviewing/approved/needs-new-photo, отмена и завершение. В деталях заявки замена фото возвращается в нужный сценарий. Checkout по request не удаляет посторонние покупки из текущей корзины.

Это не защищённая медицинская верификация: демостатус клиентский. Сервер запрещает гостю купить Rx, но не проверяет подлинность рецепта авторизованного клиента через внешний сервис. История заявок только в текущей вкладке; закрытие вкладки её очищает. Order в MongoDB при этом сохраняется независимо.

## 9. Checkout, оплата, результаты и заказы

Обычный нерецептурный заказ разрешён гостю. Контакты: имя/телефон обязательны, email необязателен. Самовывоз — бесплатно, курьер — 59 грн с городом/адресом. Карта — локальный рисунок с тремя demo-аптеками/маркерами и zoom; внешних запросов карты нет. Получение/оплата — доступные native radio с точным selected SVG 22×22 из Figma.

`POST /api/orders` валидирует поля и количества, заново получает цены, списывает склад/создаёт заказ транзакцией. Сетевое повторение POST после потери успешного ответа пока НЕ защищено idempotency key — не путать с защитой повторного клика и атомарностью склада.

checkoutStore сохраняет receipt ДО очистки купленных строк. `/order/result` читает receipt текущей вкладки, а не публичную БД по обычному ID. Снимок пользовательского заказа проверяет ownerId. Гостю история в аккаунте не создаётся. Администратор видит гостевые заказы через защищённый `GET /api/orders?admin=true`. Публичный поиск заказа по ID не добавлять.

Онлайн-оплата исключительно учебная: 4242 4242 4242 4242 → успех; 4000 0000 0000 0002 → отказ; будущий MM/YY (например 12/35) и 3 тестовые цифры CVV. Остальные номера не проходят валидацию. Номер/CVV не отправляются в API, там только demo outcome. Деньги не списываются.

Отказ оплаты сохраняет Order; «Повторити оплату» открывает новую пустую форму карты, а не автоматически оплачивает. Успех/повторный отказ работают для того же заказа. Доступ повтора — владелец/ADMIN либо гостевой секрет, хеш которого хранится в БД; обычного ID недостаточно. Отменённый/завершённый заказ не оплачивается повтором. При отмене оплаченного demo-заказа отображается demoRefundStatus=pending, без настоящего возврата банка.

OrderResult: подтверждение, товары/суммы/получение/контакты/номер и копирование, 3 из 5 → раскрыть все. При отказе оплаты красный крест 24×24 на круге 64×64, заголовок «Замовлення збережено» сохранён, потому что заказ действительно уже создан.

Статусы склада: PENDING, CONFIRMED, READY_FOR_PICKUP, SHIPPED, COMPLETED, CANCELLED. Оплата/возврат — отдельные поля checkout, а не новые статусы склада. Детали и уведомления формирует `src/lib/order-display.ts`.

В локальном аккаунте Антон Тарас созданы 9 помеченных demo-заказов (обработка, подтверждение, выдача, курьер, получение, отмена, paid, failed, возврат). Скрипт `seed-local-order-states.mjs <existing-user-id> --apply` повторяемый: не сбрасывает уже проверенные состояния, не трогает настоящие заказы. Использует отдельный скрытый demo-товар, поэтому отмена не изменяет настоящий каталог. Эти документы БД НЕ загружаются в Git вместе со скриптом.

## 11. Запуск существующего окружения

В PowerShell перейти именно в `D:\ycheba\4kurs\ux ui\iapteca`. Docker Desktop должен работать. Первоначальный setup уже выполнен, повторять его нельзя.

```powershell
git status --short --branch
docker compose --env-file .env.local config --quiet
docker compose --env-file .env.local up -d mongo
docker compose --env-file .env.local ps
pnpm dev
```

Проверять http://localhost:3000. Если сервер уже работает, второй экземпляр не запускать.

MongoDB: 7.0, rs0 PRIMARY, loopback 127.0.0.1:27017, БД iapteca, свой admin и readWrite-пользователь приложения. URI использует localhost/rs0/authSource=iapteca; hostname Docker `mongo` для Windows не использовать. Постоянный volume `iapteca_ux_ui_mongo_data`. Старый `iapteca_mongo_data` не подключать/не удалять. Остановка `docker compose --env-file .env.local stop mongo` сохраняет данные. `down -v` запрещён для сохранения БД.

`.env.local` и `.local/mongo-keyfile` уже существуют только на компьютере. При переносе на другой компьютер нужны свои секреты и либо безопасный backup, либо новый локальный seed. Clone репозитория не копирует MongoDB. Для совершенно чистого окружения читать `docs/local-development.md`, не выполнять setup поверх существующего volume.

Скрипты (не запускать автоматически только ради передачи): `pnpm seed:local`, `seed-local-bundles.mjs`, `prepare-email-auth.mjs`, `categorize-local-catalog.mjs`, `update-local-prescriptions.mjs`. Они имеют разные области действия; сначала читать документацию/preview. Seed insert-only не обновляет автоматически уже вручную исправленные поля и остатки.

Интеграционные проверки требуют запущенных localhost и rs0: `test-local-auth.mjs`, `test-local-catalog.mjs`, `test-local-bundle-orders.mjs`, `test-local-order-cancellation.mjs`. ## 13. Технический остаток вне прямого переноса макетов

1. **Защита повторного создания заказа после потери ответа** — серверный idempotency key, отдельно от существующих транзакций/защиты double-click.
2. **Данные каталога** — неполные manufacturer/country/ATC и другие поля, ограничения демонстрационного ассортимента. Проверенные источники и реальные packshot, никаких случайных медицинских фактов.
3. **A11y-аудит** — базовая семантика/labels/focus/alt присутствуют; завершить весь главный flow без мыши, focus после модалок/ошибок, contrast WCAG AA 4.5:1 и Lighthouse/axe. Не объявлять соответствие стандарту без проверки.
4. **UX-валидация** — по заданию 3–5 пользователей ИЛИ оценка по 10 эвристикам Нильсена; документировать проблемы и реально внесённые исправления. Такая завершённая валидация сейчас не подтверждена.
5. **Мобильная адаптация** — позже, по согласованным Mobile-макетам; обязательна для сдачи, существующий desktop не считать готовым mobile.
6. **Production и build** — ещё не настроены/последним этапом не проверены. Публикация Next.js и отдельная доступная production MongoDB с транзакциями; локальный Docker на Windows не является интернет-БД. Kubernetes не нужен. Простой будущий вариант — Next.js hosting + MongoDB replica set managed service, выбирать отдельно по актуальным условиям.
7. **Документация** — обновить ранние утверждения architecture/authentication/prescriptions/bundles и исторические статусы карты: восстановление UI, checkout, Bundle и пользовательская отмена уже сделаны. Не удалять полезную историю без причины.
8. Дополнительно, если потребуется: административное редактирование Bundle, серверная история рецептов/избранного между устройствами, настоящие почта/банк/фармацевт. Они НЕ входят автоматически в текущий разрешённый demo-объём.
